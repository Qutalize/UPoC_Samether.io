## 2. 改修が重くなりそうな部分（要注意ポイント）

### 2.1 `hub.go`（765行）のステージ対応 — 最重量
現状は **1プロセス1Hub1ワールド** 前提（`main.go` で `NewHub` を1つ生成し `/ws` に直結）。ステージ7〜8個をECSタスク8個で動かすのはコスト・運用的に非現実的なので、**1プロセス内に stageID→Hub のマップを持つ** 方式を推奨:

```go
// main.go 側のイメージ
hubs := map[int]*sws.Hub{}
for _, st := range stages.All() {
    h := sws.NewHub(cfgForStage(st)) // WorldWidth等をステージ定義から
    go h.Run()
    hubs[st.ID] = h
}
mux.HandleFunc("/ws", func(w http.ResponseWriter, r *http.Request) {
    id, _ := strconv.Atoi(r.URL.Query().Get("stage"))
    hub, ok := hubs[id]
    if !ok { http.Error(w, "unknown stage", 400); return }
    hub.ServeWS(w, r)
})
```

Hub自体はほぼ無改修で済みますが、注意点が2つ:
- **Redisキーの衝突**: リーダーボードの `RedisPrefix` をステージ別に分ける（`uecport:lb:stage-2` など）
- **メモリ/goroutine**: 8ワールド分のGameLoopが常時回る。フードスポーン数を控えめにすれば問題ない規模だが、プレイヤー0人のステージはloopをidle化する最適化を入れると安心（なくても動く）

### 2.3 認証が「名前をlocalStorageに保存するだけ」
`storage/auth.ts` はユーザー名のみのクライアント保持で、**進捗をサーバーに保存すると名前の詐称・衝突がそのまま進捗の乗っ取りになります**。ハッカソン版の割り切りとしては許容範囲ですが、最低限:
- 初回ログイン時にサーバーでランダムトークンを発行し `localStorage` に保存、以降のWS接続・/api/verify にトークンを付ける（Redis: `token→userID`）
- 実装1〜2時間で済み、審査で「不正対策は？」と聞かれたとき答えられる

背景シェーダ・HUD色替え程度なら安全ですが、ワールド境界やステージ演出をここに足すと肥大化します。ボス演出などは別ファイル（`effects/BossIntro.ts` 等）に切り出してください。

## 3. 画像照合ロジックの技術アドバイス（本プロジェクトの肝）

### 3.1 推奨アーキテクチャ: 「位置で厳密に、画像はゆるく」
経験則として、屋外写真の照合は**天候・時間帯・撮影距離で大きくブレます**。照合単体で厳密判定しようとすると現地で「解放できない！」が頻発し体験が崩壊します。推奨は二段構え:

1. **主判定 = ジオフェンス**（スポットから150m以内。サーバー側でHaversine。既存 `cp/distance.go` 流用）— これで「現地に行った」は担保される
2. **副判定 = perceptual hash 照合**（しきい値ゆるめ）— 「指定アングルで撮った」体験と、遠隔地からの適当な写真の排除

### 3.2 推奨ライブラリ: goimagehash（Go・サーバー側）
- `github.com/corona10/goimagehash` — pure Go（cgo不要、既存DockerfileのままビルドOK）
- pHash / dHash / aHash を数十msで計算。**dHash + pHash の2種併用**が屋外写真では安定しやすい

```go
import (
    "image/jpeg"
    "github.com/corona10/goimagehash"
)

func verifyPhoto(uploaded image.Image, refs []image.Image) bool {
    up, _ := goimagehash.PerceptionHash(uploaded)
    for _, ref := range refs {
        rh, _ := goimagehash.PerceptionHash(ref)
        d, _ := up.Distance(rh) // ハミング距離 0〜64
        if d <= 20 { // しきい値は現地サンプルで要調整（開始値18〜22）
            return true
        }
    }
    return false
}
```

運用のコツ:
- **参照画像は1スポットにつき2〜3枚**（晴れ/曇り、午前/午後）用意し、どれか1枚と一致すればOKにする
- しきい値は「正解写真20枚・無関係写真20枚」の距離分布を実測して決める（工程表 3-7）。pHashのハミング距離は無関係画像同士でも28〜36程度に収まることが多く、20前後に分離帯ができるのが典型
- **精度が出なかったときの逃げ道**: しきい値を32まで緩めて実質ジオフェンス主判定に切替（コード変更なしで運用対応できる）

### 3.3 やらないほうがよい選択肢
| 選択肢 | 見送り理由 |
|---|---|
| クライアント側(JS)でのハッシュ照合 | 参照ハッシュ・しきい値が丸見えで改ざん自由。判定は必ずサーバーで |
| OpenCV特徴点マッチング（ORB/SIFT）をWASMで | 精度は上がるが実装・チューニング工数が重い。5週間の学生チームには過剰 |
| Amazon Rekognition CompareFaces/CustomLabels | 建物照合には不向き/学習データ準備が重い + 従量課金。pHashで十分 |
| GPS常時トラッキング | 前提どおりiOS Safariのバックグラウンド制約で不可。単発 `getCurrentPosition` のみ使用 |

### 3.4 アップロード経路
- クライアント: `<input type="file" accept="image/*" capture="environment">` → Canvasで**長辺1280pxにリサイズ・JPEG再圧縮してから送信**（モバイル写真は元5〜10MBあるため。通信量と照合の安定性の両方に効く。リサイズは照合精度にほぼ影響しない）
- サーバー: `POST /api/verify` に multipart（photo, spotId, lat, lon, token）。`r.ParseMultipartForm(6<<20)` + MIME検証
- 投稿写真の保存は**必須ではない**（照合はメモリ上で完結可能）。シェア機能はクライアント側に元写真があるのでS3保存なしでも成立します。監査用に残すならS3+7日ライフサイクル

### 4.2 SNSシェア + ボーナス（F-09/F-10）
- 第一選択: **Web Share API Level 2**（`navigator.share({ files: [photoFile], text, url })`）。iOS Safari / Android Chromeとも写真添付シェアに対応。撮影に使ったFileオブジェクトをそのまま渡せる
- fallback: `https://twitter.com/intent/tweet?text=...&url=...`（写真は添付不可、テキスト+URLのみ）
- **注意**: Xに実際に投稿されたかの検証はX APIが有料のため不可能。「share()のPromiseがresolveした時点（=シェアシートで送信完了）で+100pt」に仕様を割り切り、スポットごとに1回制限（Redis SETで重複防止）にするのが現実解です
- ハッシュタグ例: `#調布のうみ #UECPort #調布市郷土博物館` — 博物館側と事前合意しておくと審査アピールになります

### 4.4 進捗永続化（F-13）
既存 `session/redis_cp.go` のパターンを踏襲して `internal/progress/store.go` を追加:
- `HSET uecport:user:{token} unlocked "1,2" points 350`
- `SADD uecport:shared:{token} spot2`（シェア重複防止）
- WSメッセージは既存の `type/payload` 規約（`protocol.ts` ⇔ `message.go` のミラー構造）に従って `progress_get` / `progress` / `points_award` / `join_rejected` / `share_done` を追加（型は `data/uecport-types.ts` §5 が正）。**両ファイルを同時に更新する規約を崩さない**こと

### 4.5 Bot補充（F-11）
`hub.go` のtick処理（`h.world.UpdateBots()` 呼び出し付近）に:

```go
if humans := h.humanCount(); humans > 0 && humans+h.botCount() < minPopulation {
    h.spawnBot() // allocBotID + randomBotRoute の既存部品で構成
}
```
人間0人のときはBotも湧かせない（サーバー負荷とリーダーボード汚染の防止)。ボス（深大寺）はこのBotに `Stage: 最大値` と追跡AIを与えた特殊個体として実装すると新規コード最小で済みます。

## 5. 開発環境Tips
- 照合APIのローカルテストは実写真が要るので、**スマホ→PCへの写真転送を待たずに済むよう** `curl -F photo=@test.jpg -F lat=... /api/verify` のMakefileターゲットを作っておくと回転が速い
- 位置情報はHTTPS必須（localhostは例外で動く）。実機テストは `vite --host` + ngrok等のHTTPSトンネル、または既存dev環境デプロイで
- デモ用に `?demo=1` で照合・ジオフェンスをスキップできる隠しフラグを用意（審査会場は調布市内とは限らないため。工程表 5-5）
