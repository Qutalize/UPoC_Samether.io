# UECPort_Samezario データ構造設計書

**成果物一式**: 本書 + `uecport-types.ts`（型定義）+ `stages.master.json`（マスタ）+ `verify.server.json`（サーバー秘匿）+ `progress.mock.json`（進捗モック）

## 0. 既存コードベースの状態管理パターン（解析結果）

設計の前提として、サメザリオには**Reactも状態管理ライブラリも存在しません**。実際のパターンは次の4本柱で、新データ構造はこれに接木します。

| パターン | 実装箇所 | 内容 |
|---|---|---|
| **サーバー権威 + クライアント射影** | `GameState.ts` | エンティティの真実はサーバー（`shark.go`/`loop.go`）。クライアントは `Map<string, Shark>` を保持し、`applyFullState`（全量）/ `applyStateDelta`（差分）でIDベースにupsert/削除 |
| **プロトコルのミラー規約** | `protocol.ts` ⇔ `message.go` | `{type, payload}` 形式。両ファイルを対で編集する運用 |
| **関心事ごとのstorageモジュール** | `storage/auth.ts`, `storage/cp.ts` | localStorageのキーを1モジュールが専有し、load/save関数のみ公開 |
| **シングルトン接続** | `websocket.ts` の `export const net` | アプリで1本のWS。`onMessage`購読 + `waitFor(type)` |

この解析から導いた設計原則:

1. **ロック状態はどこにも保存しない** — マスタは不変、進捗（`unlockedAreaIds`）から `deriveAreaState()` で毎回計算する。「マスタに `locked: boolean` を持つ」設計はマルチユーザーで即破綻するため採らない
2. **進捗の真実はサーバー（Redis）** — クライアントの `ProgressStore` は `GameState` と同じ「射影キャッシュ」として実装し、既存アーキテクチャと相似形にする
3. **照合の答え（参照画像・しきい値）は型レベルで隔離** — `SpotMaster`（公開）と `SpotVerifySecret`（サーバー専用）を別ファイル・別型に分ける

## 1. TypeScript型定義

完全版は **`uecport-types.ts`**（配置先: `client/src/data/types.ts`。WSペイロード部分は既存規約に従い `network/protocol.ts` へ移すこと）。ここでは設計判断のみ解説します。

### 1.1 エリア（`AreaMaster`）— 要件2に対応
- `id: number` は改修手順書の `/ws?stage=N`・Redisキーと一致させる。`slug` は画像パス・CSSクラス用
- `towns: string[]` で「属する市町名」（調布ヶ丘・布田・小島町 等）を保持
- `requires: AreaId[]` + `unlockSpotId` で「にゃんこ大戦争風」の進行グラフを表現。**ロック状態フィールドは持たない**（`deriveAreaState()` が `unlocked / unlockable / locked / boss-sealed` の4状態を返す）
- `worldSize` で初期エリアの狭さ（1200）〜ボスの広さ（5000）をデータ駆動に。`minPopulation` はbot補充の閾値

### 1.2 歴史スポット（`SpotMaster` / `SpotVerifySecret`）— 要件3に対応
- 公開側: 位置・ジオフェンス半径・獲得ポイント（`clearPoints`/`sharePoints`）・お手本画像・撮影ガイド・解説文・カテゴリ
- **「SNSシェア状態」はマスタに置かない** — シェア済みかはユーザーごとの事実なので `UserProgress.clearedSpots[].shared` に置く（要件3の「シェア状態」はここで満たす）
- 秘匿側（サーバー専用型）: 参照画像メタデータ（撮影条件つき、チューニング記録を兼ねる）と `phashThreshold`

### 1.3 ユーザー進捗（`UserProgress`）— 要件1に対応
- `points` / `unlockedAreaIds` / `clearedSpots: Record<SpotId, SpotClearRecord>` の3点が中核
- `clearedSpots` を配列でなくRecordにしたのは、照合成功時のupsertと「クリア済み？」参照がO(1)になり、`GameState` のMapパターンと揃うため
- `version: 1` を必ず持たせる（審査直前のスキーマ変更でlocalStorageキャッシュが壊れる事故の予防）

### 1.4 ゲーム内エンティティ — 要件4に対応
- **新型を作らず既存 `StateSharkView` に3フィールド追加**（`isBot` / `isBoss` / `skin`）。`GameState.ts` の `getOrCreateShark()` がそのまま流用でき、改修が最小になる
  - 現状クライアントはbotを見た目で区別できない（`getDummyRoute()` でルートを推測しているだけ）。`isBot` をサーバーが明示すれば名札色分けが正しくなる
- bot の出現定義は `BotProfile`（エリア別の名前接頭辞・進化段階レンジ・スキン・攻撃性、ボス定義）としてマスタに同梱。サーバーの `UpdateBots`/`allocBotID` がこれを読む

### 1.5 通信路の型
- WS追加分: `JoinMsg`（`stageId`/`token`追加）、`progress` / `points_award` / `join_rejected` / `share_done` — **`message.go` と対で追加**
- HTTP: `VerifyRequest` / `VerifyResponse`。成功レスポンスに**更新後の `UserProgress` 全体を同梱**する設計にした点が重要（クライアントは差分計算せず丸ごと上書き＝バグの温床を消す。既存の `applyFullState` と同じ思想）

## 2. 初期状態・マスターデータのJSONモック

3ファイルに分割しています（**分割自体が設計**です）:

| ファイル | 配置先 | 中身 |
|---|---|---|
| `stages.master.json` | `client/public/` + サーバーembed（同一ファイル） | 全8エリア（調布・京王多摩川・国領・柴崎・つつじヶ丘・西調布・飛田給・深大寺）、9スポット、botプロファイル。実在地名・実座標入り |
| `verify.server.json` | `server/internal/verify/` のみ | 参照画像メタ + pHashしきい値（スポット特性に応じ18〜24で差をつけた根拠つき） |
| `progress.mock.json` | テスト・シード用 | `initial`（新規: エリア1のみ解放・0pt）と `midGame`（3エリア解放・460pt・シェア済み2件）。midGameには `deriveAreaState()` の期待値も注記 |

マスタの見どころ:
- **調布駅エリア（調布ヶ丘・布田・小島町）が初期解放**で、`worldSize: 1200` により「最初は駅前の狭い範囲だけ」を表現。エリア内に布多天神社をチュートリアルスポットとして内包（解放条件には使わないがポイントが稼げる）
- **郷土博物館（小島町3丁目）は京王多摩川エリアの解放スポット** — 実際の所在地が京王多摩川駅徒歩圏のため。連携先を序盤の必須動線に置く意図もある
- 進行グラフ: `1 → {2, 3, 6}` と枝分かれし、`3→4→5`、`6→7`、全踏破で `8`（深大寺）。西と東どちらから攻めてもよい回遊設計
- 深大寺はボス定義（`深大寺のヌシ` / megalodon / 討伐500pt）を同梱

## 3. 状態管理（State Management）の設計案

### 3.1 どこで・どう管理するか — 3層構造

```
[第1層] マスタ（不変）        data/master.ts
  起動時に stages.master.json を fetch → freeze。
  提供: getArea(id) / getSpot(id) / spotsInArea(id) / deriveAreaState(...)

[第2層] ユーザー進捗（サーバー権威の射影）   storage/progress.ts = ProgressStore
  シングルトン + Phaser.Events.EventEmitter。
  ・メモリ上に UserProgress を1つ保持
  ・localStorage("uecport_progress_v1") はオフライン表示用キャッシュに過ぎない
  ・更新経路は「サーバーから丸ごと受信 → replace() → emit("changed")」のみ

[第3層] ゲーム内エンティティ（既存のまま）   game/state/GameState.ts
  変更は StateSharkView への isBot/isBoss/skin 追加と名札の出し分けだけ。
  進捗とは意図的に分離（プレイ中に進捗が変わることはない）
```

`ProgressStore` の骨子（既存 `GameState` / `storage/*` の流儀と相似形）:

```ts
// client/src/storage/progress.ts
import Phaser from "phaser";
import type { UserProgress, AreaId, SpotId } from "../data/types";

const CACHE_KEY = "uecport_progress_v1";

class ProgressStore extends Phaser.Events.EventEmitter {
  private p: UserProgress | null = null;

  /** 唯一の書き込み口。サーバー発スナップショットで丸ごと置換 */
  replace(next: UserProgress): void {
    this.p = next;
    localStorage.setItem(CACHE_KEY, JSON.stringify(next));
    this.emit("changed", next);
  }

  /** 起動直後のオフライン表示用（真実はこの後の progress 受信で上書き） */
  loadCache(): UserProgress | null {
    try {
      const raw = localStorage.getItem(CACHE_KEY);
      const v = raw ? JSON.parse(raw) : null;
      if (v?.version === 1) this.p = v;
    } catch { /* 壊れたキャッシュは無視 */ }
    return this.p;
  }

  get(): UserProgress | null { return this.p; }
  isUnlocked(id: AreaId): boolean { return !!this.p?.unlockedAreaIds.includes(id); }
  isCleared(id: SpotId): boolean { return !!this.p?.clearedSpots[id]; }
  points(): number { return this.p?.points ?? 0; }
}
export const progressStore = new ProgressStore(); // net と同じシングルトン様式
```

Sceneの購読パターン（HUDのポイント表示など）:

```ts
create() {
  progressStore.on("changed", this.onProgress, this);
  this.events.once(Phaser.Scenes.Events.SHUTDOWN,
    () => progressStore.off("changed", this.onProgress, this)); // 既存Sceneと同じ後始末様式
}
```

### 3.2 「写真照合が成功した時」のデータフロー

```
UnlockScreen                photoVerify.ts        POST /api/verify      Redis
    │ [撮影ボタン]                │                  (Go: verify/)         │
    │──getCurrentPosition()──▶   │                       │                │
    │   （iOS要件: ボタンハンドラ内で呼ぶ）               │                │
    │──verify(spotId,file)──────▶│──multipart──────────▶│                │
    │                            │      ①ジオフェンス判定(Haversine≦150m) │
    │                            │      ②pHash照合(dist≦threshold)        │
    │                            │      ③進捗更新────────────────────────▶│
    │                            │         HSET points/unlocked/clear     │
    │                            │      ④更新後のUserProgress全体を構築    │
    │◀──VerifyResponse{ok:true, unlockedAreaId:2, progress:{...}}──────── │
    │                            │
    │ progressStore.replace(res.progress)   ← ★唯一の更新点★
    │      └─ emit("changed") → 購読中の全Scene(HUD等)が自動反映
    │
    │ scene.start("UnlockSuccessScreen", {spotId, unlockedAreaId, photoFile})
    │      └─ 解放演出 → シェアボタン
    │
    │ [シェア成功] net.send({type:"share_done", payload:{spotId}})
    │      Server: 重複チェック(SADD) → +100pt → "progress"スナップショット再配信
    │      └─ クライアント: progressStore.replace() （同じ一本道で反映）
    │
    │ 「マップに戻る」→ StageMapScreen.create()
    │      └─ deriveAreaState(area, progressStore.get(), areas) を全エリアで評価
    │         2番が locked → unlocked に変わっている → グレーマスク除去 + 赤ピンdropPin()
```

この設計の要点は3つです。

1. **書き込み口が `progressStore.replace()` の一本しかない** — 照合成功・シェアボーナス・ログイン時の`progress`受信、すべて「サーバーが作った完全なスナップショットで置換」。クライアントで `points += 100` のような差分加算は**しない**（二重加算・不整合バグを構造的に排除。既存 `applyFullState` と同じ哲学）
2. **楽観更新をあえてしない** — 照合は結果が2〜3秒で返り、失敗もありうる操作なので、ローディング表示で待つ方がUXも実装も安全
3. **マップ画面は「状態を持たない」** — StageMapScreenは毎回 `deriveAreaState()` を評価して描くだけ。解放演出のトリガーは `scene.start` のdata（`unlockedAreaId`）で受け渡す

### 3.3 補足: Reactでモックを作る場合の対応表

プレゼン用モックアップ（前回のアーティファクト）や、将来React化する場合は次の写像になります:

| 本設計（Phaser） | React equivalent |
|---|---|
| `data/master.ts`（不変マスタ） | モジュールスコープ定数（stateにしない） |
| `progressStore` + `emit("changed")` | `ProgressContext` + `useReducer`（actionは `REPLACE_PROGRESS` の1種類だけ、という点が本設計の肝の直訳） |
| `deriveAreaState()` | そのまま流用（純関数なので環境非依存） |
| `GameState`のMap | ゲーム部はPhaserのまま埋め込むため対応不要 |

`uecport-types.ts` と `deriveAreaState` は純TypeScriptなので、Phaser本体・Reactモック・（型をコメント翻訳すれば）Goサーバーの3者で同一の語彙を共有できます。
