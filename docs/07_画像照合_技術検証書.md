# UECPort_Samezario 画像照合機能 技術検証書

**対象**: 写真撮影によるエリア解放（チェックイン方式）のフロントエンド中心実装
**結論（先出し）**:
- カメラ起動は **`<input type="file" capture="environment">` 一択**（getUserMediaは使わない）
- 照合は **ブラウザ内 dHash（perceptual hash）比較** をまず実装（追加インフラ・費用ゼロ、1日で動く）
- Rekognition（案B）は「特定の建物か」の判定には**構造的に不向き**（後述）。採るなら補助判定のみ
- ハッカソン本番構成は「**位置チェック（厳密）+ dHash（ゆるく）**」の二段構え。dHash計算を既存Goサーバーに移すのは関数1個分の作業で、段階移行できる

> 付属の **「照合ラボ」デモ（React artifact）** で、実際の写真2枚を使ってハミング距離としきい値を今すぐ検証できます。W3のしきい値チューニング作業はこのツールで完結します。

## 1. Webアプリでのカメラ起動と画像取得

### 1.1 方式比較 — なぜ `<input capture>` なのか

| | `<input type="file" capture>` | `getUserMedia`（WebRTC） |
|---|---|---|
| iOS Safari | ◎ OS標準カメラが起動。権限UI・ピント・HDRすべてOS任せ | △ 動くが権限拒否・回転・タブ復帰など地雷多数 |
| Android Chrome | ◎ 同上 | ○ |
| 実装量 | **約20行** | 200行超（video要素、stream管理、canvas取り出し、後始末） |
| 失敗モード | ユーザーがキャンセルする、のみ | NotAllowedError / NotReadableError / デバイス切替 / 画面ロック復帰… |
| 取れるもの | `File`（JPEG。EXIF付き） | フレームのcanvasキャプチャ |

照合用途は「1枚撮れればいい」ので、プレビューをアプリ内に埋め込む必要のあるgetUserMediaを選ぶ理由がありません。**最もエラーが起きにくいのはOSのカメラUIに丸投げする`<input>`方式**です。

### 1.2 実装コード

コアはフレームワーク非依存の関数にし（既存Phaser側でもそのまま使えます）、Reactはそれを包むhookにします。

```ts
// services/camera.ts —— フレームワーク非依存
/**
 * OSカメラ（またはギャラリー）を起動して File を1枚取得する。
 * 必ずユーザー操作（クリックハンドラ）内から呼ぶこと。
 * キャンセル時は null を返す（rejectしない: キャンセルは異常系ではない）。
 */
export function capturePhoto(useCameraDirect = true): Promise<File | null> {
  return new Promise((resolve) => {
    const input = document.createElement("input");
    input.type = "file";
    input.accept = "image/*";
    if (useCameraDirect) input.setAttribute("capture", "environment"); // 背面カメラ直起動
    input.style.display = "none";
    document.body.appendChild(input);

    const cleanup = () => input.remove();

    input.onchange = () => {
      const file = input.files?.[0] ?? null;
      cleanup();
      resolve(file);
    };
    // iOS Safariはキャンセル時にchangeが発火しないため、フォーカス復帰で検知
    window.addEventListener("focus", () => {
      setTimeout(() => {
        if (!input.files?.length) { cleanup(); resolve(null); }
      }, 300);
    }, { once: true });

    input.click();
  });
}
```

```tsx
// hooks/useCameraCapture.ts —— React用ラッパ
import { useState, useCallback } from "react";
import { capturePhoto } from "../services/camera";

export function useCameraCapture() {
  const [file, setFile] = useState<File | null>(null);
  const [previewUrl, setPreviewUrl] = useState<string | null>(null);

  const capture = useCallback(async () => {
    const f = await capturePhoto();
    if (!f) return null;                       // キャンセル
    setFile(f);
    setPreviewUrl((old) => {
      if (old) URL.revokeObjectURL(old);       // メモリリーク防止
      return URL.createObjectURL(f);
    });
    return f;
  }, []);

  const reset = useCallback(() => {
    setPreviewUrl((old) => { if (old) URL.revokeObjectURL(old); return null; });
    setFile(null);
  }, []);

  return { file, previewUrl, capture, reset };
}
```

## 2. 現実的かつ軽量な画像照合ロジック

### 2.0 3案の比較と推奨

| | 案A: ブラウザ内 dHash | 案B: Rekognition | 案C: 既存GoサーバーでdHash |
|---|---|---|---|
| 実装工数 | **半日〜1日** | 1〜2日（Lambda+IAM+API GW） | 案A完成後 **+半日** |
| 追加費用 | 0円 | 従量課金（$1/1000枚〜） | 0円 |
| 「特定の建物か」精度 | ○（アングル指定前提で実用域） | **×**（後述） | ○ |
| 不正耐性 | ×（答えがバンドルに入る） | ○ | ○ |
| 追加インフラ | なし | Lambda/API GW/IAM | なし（既存ECSにhandler追加） |

**推奨ロードマップ**: まず案Aで全フローを動かす（デモ可能状態を最速で作る）→ ハッカソン提出までに照合関数だけ案Cへ移動（判定を秘匿化）。案A/Cはアルゴリズムが同一なので、しきい値チューニングの成果がそのまま持ち越せます。

**案Bの構造的問題**: Rekognitionの`DetectLabels`が返すのは「Building」「Shrine」「Architecture」のような**一般ラベル**です。「これは*調布市郷土博物館*か？」ではなく「これは何かの建物か？」しか判定できず、隣町の博物館でも通ってしまいます。特定被写体の照合には`Custom Labels`（要学習・時間課金でハッカソン予算外）が必要になり、コスパが崩壊します。使うなら「建物すら写っていない写真を弾く」補助フィルタ止まりです。

### 2.1 案A: ブラウザ内 dHash 照合（推奨・第一段階）

dHash（difference hash）は「画像を9×8のグレースケールに縮小し、隣接ピクセルの明暗差64bitをハッシュ化」する手法です。縮小してから比較するため、**解像度・多少のアングルずれ・明るさ変化に強い**のが特徴で、canvasだけで実装できます。

```ts
// services/imageHash.ts —— 依存ライブラリゼロ
/** File/Blob → 64bit dHash（bigint） */
export async function computeDHash(source: Blob): Promise<bigint> {
  // EXIF回転を正しく適用してデコード（iOS縦持ち写真対策）
  const bmp = await createImageBitmap(source, { imageOrientation: "from-image" });

  const W = 9, H = 8;
  const canvas = document.createElement("canvas");
  canvas.width = W; canvas.height = H;
  const ctx = canvas.getContext("2d", { willReadFrequently: true })!;
  ctx.drawImage(bmp, 0, 0, W, H);
  bmp.close();

  const { data } = ctx.getImageData(0, 0, W, H);
  // グレースケール化（ITU-R BT.601）
  const gray = new Float64Array(W * H);
  for (let i = 0; i < W * H; i++) {
    gray[i] = 0.299 * data[i * 4] + 0.587 * data[i * 4 + 1] + 0.114 * data[i * 4 + 2];
  }
  // 隣接差分 → 64bit
  let hash = 0n;
  for (let y = 0; y < H; y++) {
    for (let x = 0; x < W - 1; x++) {
      hash = (hash << 1n) | (gray[y * W + x] < gray[y * W + x + 1] ? 1n : 0n);
    }
  }
  return hash;
}

/** ハミング距離（0=完全一致, 64=全ビット不一致） */
export function hammingDistance(a: bigint, b: bigint): number {
  let x = a ^ b, d = 0;
  while (x) { d += Number(x & 1n); x >>= 1n; }
  return d;
}

/** 照合判定: 参照ハッシュ群のどれかがしきい値内なら合格 */
export function matchAny(
  target: bigint,
  refs: bigint[],
  threshold = 14,           // dHashはpHashより分離が良く、初期値14前後から調整
): { ok: boolean; best: number } {
  const best = Math.min(...refs.map((r) => hammingDistance(target, r)));
  return { ok: best <= threshold, best };
}
```

**ハッカソン用ダミー判定の同居**: デモ会場（調布市外）や開発中は本物の照合を通せないので、判定関数を1枚抽象化しておきます。

```ts
// services/verifier.ts
export interface VerifyOutcome { ok: boolean; matchScore: number; error?: "NO_MATCH" }

const DEMO_MODE = new URLSearchParams(location.search).has("demo");

export async function verifyPhoto(photo: Blob, refHashes: bigint[]): Promise<VerifyOutcome> {
  if (DEMO_MODE) {                                   // ?demo=1 → 2秒待って必ず成功
    await new Promise((r) => setTimeout(r, 2000));
    return { ok: true, matchScore: 92 };
  }
  const hash = await computeDHash(photo);
  const { ok, best } = matchAny(hash, refHashes);
  return ok
    ? { ok: true, matchScore: Math.round(100 - (best / 64) * 100) }
    : { ok: false, matchScore: Math.round(100 - (best / 64) * 100), error: "NO_MATCH" };
}
```

参照ハッシュは、参照画像をビルド時に一度計算して定数化します（`bigint`は`"0x3f2a..."`文字列でJSONに載せて`BigInt(s)`で復元）。**注意: この方式では参照ハッシュとしきい値がバンドルに含まれる**ため、判定の答えが見える状態です。ハッカソンのPoCとしては許容し、案Cへの移行で解消します。

### 2.2 案C: 判定を既存Goサーバーへ移す（提出版）

既存の`server/cmd/server/main.go`にhandlerを1つ足すだけです（新サーバー構築は不要）。アルゴリズムは案Aと同一なので、`github.com/corona10/goimagehash`（pure Go・cgo不要、既存Dockerfileのままビルド可）の`DifferenceHash`を使えばしきい値も持ち越せます。

```go
// server/internal/verify/handler.go（骨子）
func (h *Handler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
    r.Body = http.MaxBytesReader(w, r.Body, 6<<20)
    if err := r.ParseMultipartForm(6 << 20); err != nil { badRequest(w, "BAD_IMAGE"); return }

    // ① ジオフェンス（answer: 位置は厳密に）
    lat, lon := parseF(r, "lat"), parseF(r, "lon")
    spot := h.spots[r.FormValue("spotId")]
    if dist := haversineM(lat, lon, spot.Lat, spot.Lon); dist > spot.GeofenceM {
        writeJSON(w, VerifyResp{OK: false, Error: "TOO_FAR", DistanceM: dist - spot.GeofenceM}); return
    }
    // ② dHash（answer: 画像はゆるく）
    f, _, _ := r.FormFile("photo")
    img, _, err := image.Decode(f)
    if err != nil { badRequest(w, "BAD_IMAGE"); return }
    hash, _ := goimagehash.DifferenceHash(img)
    best := 65
    for _, ref := range h.refHashes[spot.ID] {          // 起動時に参照画像から計算済み
        if d, _ := hash.Distance(ref); d < best { best = d }
    }
    if best > spot.Threshold {
        writeJSON(w, VerifyResp{OK: false, Error: "NO_MATCH"}); return
    }
    // ③ 進捗更新して完全スナップショットを返す（データ設計書3.2のフロー）
    progress := h.progress.UnlockBySpot(r.FormValue("token"), spot.ID)
    writeJSON(w, VerifyResp{OK: true, MatchScore: 100 - best*100/64, Progress: progress})
}
```

## 3. 撮影 → 照合 → エリア解放までの一連のフロー

データ構造設計書（06）の原則「**進捗の更新はサーバー/照合結果のスナップショットで丸ごと置換、1本道**」に従ったReact実装です。

```tsx
// hooks/useUnlockFlow.ts
import { useReducer, useCallback } from "react";
import { capturePhoto } from "../services/camera";
import { resizeToJpeg } from "../services/imageResize";      // §4.2
import { getCurrentPositionOnce } from "../services/geolocation";
import { verifyPhoto } from "../services/verifier";           // 案A（案C移行時はfetchに差替え）
import type { UserProgress, SpotMaster } from "../data/types";

type Step = "idle" | "capturing" | "locating" | "verifying" | "success" | "error";
interface FlowState { step: Step; matchScore?: number; errorMsg?: string; photo?: File }

type Action =
  | { type: "STEP"; step: Step }
  | { type: "SUCCESS"; matchScore: number; photo: File }
  | { type: "ERROR"; msg: string };

function reducer(s: FlowState, a: Action): FlowState {
  switch (a.type) {
    case "STEP":    return { ...s, step: a.step, errorMsg: undefined };
    case "SUCCESS": return { step: "success", matchScore: a.matchScore, photo: a.photo };
    case "ERROR":   return { ...s, step: "error", errorMsg: a.msg };
  }
}

export function useUnlockFlow(
  spot: SpotMaster,
  refHashes: bigint[],
  onProgressReplace: (p: UserProgress) => void,   // ProgressContextのdispatch(REPLACE_PROGRESS)
) {
  const [state, dispatch] = useReducer(reducer, { step: "idle" });

  const run = useCallback(async () => {
    try {
      /* ── ① 撮影（ユーザー操作起点。この関数自体をonClickから呼ぶこと） ── */
      dispatch({ type: "STEP", step: "capturing" });
      const raw = await capturePhoto();
      if (!raw) { dispatch({ type: "STEP", step: "idle" }); return; }   // キャンセル

      /* ── ② 位置取得（撮影と同じジェスチャ文脈内で開始） ── */
      dispatch({ type: "STEP", step: "locating" });
      const pos = await getCurrentPositionOnce(8000);
      const distM = haversineM(pos.lat, pos.lon, spot.location.lat, spot.location.lon);
      if (distM > spot.geofenceM) {
        dispatch({ type: "ERROR", msg: `スポットまであと約${Math.round(distM - spot.geofenceM)}m 近づいてね` });
        return;
      }

      /* ── ③ リサイズ → 照合 ── */
      dispatch({ type: "STEP", step: "verifying" });
      const resized = await resizeToJpeg(raw, 1280, 0.85);
      const result = await verifyPhoto(resized, refHashes);
      if (!result.ok) {
        dispatch({ type: "ERROR", msg: "お手本と同じアングルで、看板や建物全体が入るように撮ってみて" });
        return;
      }

      /* ── ④ 進捗更新（案A暫定: ローカル計算 / 案C: レスポンスのprogressをそのまま渡す） ── */
      const nextProgress = await applyUnlockLocally(spot);   // 案C移行後は res.progress に置換
      onProgressReplace(nextProgress);                        // ★唯一の状態更新点★

      dispatch({ type: "SUCCESS", matchScore: result.matchScore, photo: raw });
    } catch (e) {
      dispatch({ type: "ERROR", msg: toUserMessage(e) });     // §4.4のエラー変換
    }
  }, [spot, refHashes, onProgressReplace]);

  return { state, run };
}
```

```tsx

  const { dispatch } = useProgress();  // Context: {type:"REPLACE_PROGRESS", progress} のみ受け付ける

    (p) => dispatch({ type: "REPLACE_PROGRESS", progress: p }));
```

`run`が①〜④を直列awaitする1本の非同期関数になっており、途中失敗はすべて`ERROR`ステップに集約されます。**状態更新は`onProgressReplace`の1箇所だけ**なので、案A→案Cへの移行は「④で渡すオブジェクトの出どころ」を差し替えるだけで済みます。

## 4. 技術的な注意点とトラブルシューティング

### 4.1 セキュリティ要件
- **HTTPS必須**: カメラ（input captureのカメラ直起動を含む）と`geolocation`はSecure Context限定。`http://localhost`のみ例外。実機テストは (a) dev環境へデプロイ、(b) `vite --host` + Cloudflare Tunnel等のHTTPSトンネル、のどちらかで
- **ユーザージェスチャ要件**: `getCurrentPosition`の権限プロンプトは、iOSでは**タップ等のハンドラから同期的に近い形で呼ばれないと出ない**ことがある。§3のように「撮影ボタン1回のハンドラ内で撮影→位置取得を連続実行」する構成が安全
- 権限を一度拒否されるとJSからは再要求できない。`PermissionDeniedError`時は「設定 > Safari > 位置情報 から許可してください」への誘導文を必ず用意

### 4.2 画像リサイズ（容量対策）— 実装コード

スマホ写真は5〜12MBあるため、送信前に長辺1280pxへ縮小します。dHash照合はどのみち9×8まで縮小するので**照合精度への影響はありません**。

```ts
// services/imageResize.ts
/** 長辺 maxEdge px・JPEG品質 quality に圧縮。EXIF回転も適用して「見たまま」に正規化 */
export async function resizeToJpeg(src: Blob, maxEdge = 1280, quality = 0.85): Promise<Blob> {
  const bmp = await createImageBitmap(src, { imageOrientation: "from-image" });
  const scale = Math.min(1, maxEdge / Math.max(bmp.width, bmp.height));
  const w = Math.round(bmp.width * scale), h = Math.round(bmp.height * scale);

  const canvas = document.createElement("canvas");
  canvas.width = w; canvas.height = h;
  canvas.getContext("2d")!.drawImage(bmp, 0, 0, w, h);
  bmp.close();

  const blob = await new Promise<Blob | null>((r) => canvas.toBlob(r, "image/jpeg", quality));
  if (!blob) throw new Error("RESIZE_FAILED");
  return blob;   // 実測でおおむね 150〜350KB に収まる
}
```

### 4.3 EXIF回転の罠（iOS最頻出バグ）
iPhoneの縦持ち写真は「横向きピクセル + EXIFの回転フラグ」で保存されます。素の`drawImage`はフラグを無視するため、**参照画像と90度ずれてdHashが全く合わない**事故が起きます。上のコードの `createImageBitmap(..., { imageOrientation: "from-image" })` がその対策です（iOS 15+/モダンChromeで有効）。参照ハッシュを作るときも**必ず同じ関数を通す**こと（正規化経路の不一致が最大のバグ源）。

### 4.4 その他のつまずきポイント

| 症状 | 原因と対策 |
|---|---|
| 位置取得が永遠に返らない | 屋内・機内モード。`timeout: 8000, maximumAge: 30000, enableHighAccuracy: true` を指定し、タイムアウトは「屋外で再試行してね」と案内 |
| `input`のキャンセルを検知できない | iOSは`change`が発火しない。§1.2のfocus復帰フォールバックで対応済み |
| HEICが送られてくる | `capture`付きカメラ直起動ならJPEGになる。ギャラリー選択を許すデバッグ時のみ発生しうるので、`file.type`をチェックして非JPEGは`canvas`経由で再エンコード（4.2の関数を通せば自動的にJPEG化される） |
| 夜間・雨天で照合が通らない | アルゴリズムの限界。参照画像を時間帯別に2〜3枚持つ + それでもダメなら**しきい値を上げて実質ジオフェンス主判定に逃がす**（運用で吸収できる設計にしてあるのが本構成の保険） |
| canvasのメモリ逼迫（連続撮影時） | `bmp.close()`と`URL.revokeObjectURL()`を必ず呼ぶ（コード内に組込済み） |

### 4.5 しきい値の決め方（実測手順）
1. 各スポットで「正解写真」を10〜20枚（別人・別時間帯で）、「不正解写真」を10〜20枚（隣の建物・全然違う場所）撮る
2. 付属の**照合ラボ**で総当たりのハミング距離を記録
3. 正解群の最大値 < しきい値 < 不正解群の最小値、となる値を選ぶ（分離帯がなければ参照画像を増やす）
4. dHashの経験則: 同一被写体の別撮影は距離 **6〜12**、無関係画像は **22〜32** に分布することが多く、**14前後**が初期値として妥当
